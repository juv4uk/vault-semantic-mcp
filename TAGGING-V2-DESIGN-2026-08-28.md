# Vault Auto-Tagging v2 — Design Proposal

**Статус:** PROPOSED (не реалізовано; заблоковано на завершенні фонового
індексування vault — `data/index-vault-live/vault_embeddings.jsonl`
станом на написання покриває частину з 1066 нотаток, не всі).
**Задача:** виправити реальний, живо підтверджений баг v1
(`classify_vault_semantic.py`): плоский поріг без обмеження давав
meta-документам (глосарії/індекси) 200+ тегів — технічно правильно за
правилом "більше сенсів → більше тегів", але практично марно.

**Походження:** метод Волта Діснея (Мрійник → Реаліст → Критик), три
послідовні агенти, усі на тому ж рантайм-моделі, що й координатор
(Claude Sonnet 5) — рольова/процесна різноманітність, **не**
крос-модельна перевірка.

---

## 1. Алгоритм v2 (дизайн Реаліста + 3 обов'язкові правки Критика)

Замість mean-pooled вектора нотатки + єдиний поріг:

1. **Similarity по чанках**, не по усередненому вектору — чанк-ембединги
   вже є в `vault_embeddings.jsonl`.
2. `hit(chunk, concept) = 1` при `sim ≥ 0.60`.
3. `coverage_j(N)` = частка чанків нотатки `N`, що влучають у концепт `j`;
   `peak_j(N)` = максимальна sim серед чанків.
4. `base_j` = частка чанків **усього vault**, що влучають у концепт `j`
   (один прохід по `vault_embeddings.jsonl`, кешується).
5. `rel_j(N) = coverage_j(N) / (base_j + ε)` — відносна щільність, гасить
   фонові терміни (напр. "atman", що зринає майже скрізь у
   санскрит-важкому vault).
6. Тир (лише для пар з `peak_j ≥ 0.60`): **CORE** (`peak≥0.72 AND
   rel≥2.0`) / **SUPPORTING** (`peak≥0.65 AND rel≥1.0`) / **ADJACENT**
   (нижче — лише sidecar). Ці конкретні числа — `predicted`, не
   каліброваними; потребують реального прогону проти відомих
   деградованих файлів + кількох звичайних нотаток різної "насиченості"
   перед тим, як вважатись `empirically confirmed`.

### Meta-doc виявлення (механічно, не за назвою файлу)
`breadth(N)` = кількість концептів з `peak_j ≥ 0.60`. Якщо
`breadth(N) > CAP` (запропоновано `CAP=15`, теж `predicted`) → meta-doc:
у frontmatter йде лише топ-10 CORE + один синтетичний `hub`-тег, повний
список — лише в sidecar (`all_touched_concepts`), нічого не губиться.

**Критик (Reality Checker), підтверджено CONFIRM/NARROW/CORRECT:**
- Механізм ловить обидва відомі деградовані файли (~200/270 концептів
  >> CAP=15), але **NARROW**: справді насичене есе з 20-30 легітимних
  крос-посилань теж може хибно спрацювати як meta-doc — потрібне
  тестування на різноманітних нотатках, не лише на двох відомих.
- Чанковий підхід — **не** реальна вартість по обчисленню (~1.5 млрд
  multiply-add для всього vault — мілісекунди на CPU, GPU взагалі не
  задіяний на цьому кроці).

### 3 обов'язкові правки перед реалізацією
1. **Теги `atman/core`, не `core/atman`.** Obsidian групує вкладені теги
   за лівим сегментом — клік на батьківський тег показує всі дочірні.
   Тир як лівий сегмент фрагментує один концепт по трьох різних
   "батьках"; концепт має бути зліва.
2. **Baseline (`base_j`) залежить від повноти індексу vault, а індекс
   зараз неповний.** Потрібна явна версія baseline (напр. за кількістю
   рядків `vault_embeddings.jsonl` на момент розрахунку), збережена в
   sidecar, + позначка "потребує перетегування", коли baseline суттєво
   зміниться — щоб не блокувати роботу до 100% покриття, але й не
   мовчки порівнювати непорівнянні оцінки.
3. **Meta-doc frontmatter теж іде через наявний `apply_vault_tags.py` з
   dry-run за замовчуванням** — не обходить наявний запобіжник (vault
   не під git, немає safety net).

### Представлення тегів
Sidecar (JSON, розширений): `{vault_file, is_meta_doc, breadth,
tags:[{concept,tier,peak_sim,rel_density}], hub_tag,
all_touched_concepts, status:"semantic-suggest-v2", review:"unreviewed",
baseline_version}`. Frontmatter отримує лише CORE+SUPPORTING, тир —
правий сегмент (`atman/core`). ADJACENT ніколи не потрапляє в
frontmatter. Кожна нотатка отримує `tag_source: semantic-auto-v2
(unreviewed)` — закриває розрив, де застосовані теги раніше не несли
жодної епістемічної позначки після запису в frontmatter.

### Явно відкладено (з обґрунтуванням)
LLM-генерація вільних сенсів, онтологічний граф-колапс, persistent
homology, крос-мовна тріангуляція, темпоральна акреція, рекурсивна
"фрактальна" насиченість, калібрувальний набір від власника — усе
відкладено через відсутню інфраструктуру, недоведену потребу, або як
природний наступний крок після валідації цієї першої версії.

## 2. Економна інтеграція Sarvam — лише у важких місцях

Перевірено проти вже задокументованої, емпірично підтвердженої пам'яті
про Sarvam (`~/.claude/.../memory/sarvam-mcp-integration.md`) — **не**
проти оптимістичного опису в `EXTERNAL-DOCS-SARVAM.md` цього ж репо,
який стверджує, що `translate_text` — "єдиний надійний інструмент для
семантичної роботи з sa-IN, який розрізняє тонкощі термінології". Це
суперечить нашій же зафіксованій знахідці: `sarvam-translate:v1`
сплощує філософську термінологію (dharma → просто "Religion"), тобто
грубий gloss, не надійний семантичний інструмент. Вартує окремо звірити
з Sutradhara/власником, яке з двох тверджень тримається на реальних
тестах, а яке — оптимістичний переказ документації.

Підтверджені реальні обмеження, що звужують застосування:
- `identify_language`/`translate_text` НЕ покривають українську
  взагалі — половина vault поза межами Sarvam.
- `analyze_text` не працює (404 на кожному виклику).
- `transliterate_text` дає розмовну романізацію, не IAST/SLP1.

**Дві точки застосування (не по всьому vault):**

1. **Нульові нотатки → кандидат нового терміну Онтології.**
   `NLP-ARCHITECTURE.md` §4 вже описує цей крок як потребуючий "LLM (або
   агента)" без конкретної реалізації. Для нотаток, що після v2
   отримали 0 тегів, і лише якщо в тексті детектується Devanagari/щільний
   IAST (дешева regex-перевірка, без API виклику) — один виклик
   `translate_text` (`sarvam-translate:v1`) як чорновий gloss для
   людини (чи агента), щоб запропонувати назву нового концепту. Не для
   верифікації (переклад занадто сплощений) — лише для генерації
   кандидата, який власник все одно перегляне перед створенням `.md`.

2. **Межові meta-doc випадки (breadth 12-20) — Sarvam НЕ потрібен.**
   Дешевше й надійніше: структурна евристика без API (кількість
   заголовків, слова "індекс"/"покажчик"/"таблиця"/"словник" у
   заголовку, щільність `[[wikilinks]]`).

Підсумок: один точковий, дешевий виклик Sarvam лише на залишку
нульових санскритських нотаток — заповнює вже задокументовану діру в
архітектурі, не додає AI заради AI.

## 3. Наступний крок

Заблоковано на завершенні `embed_vault_live.py` (фонове завдання,
checkpoint після кожного файлу, безпечно перервати/відновити). Коли
покриття вважатиметься достатнім — писати `classify_vault_semantic_v2.py`
+ оновлений `apply_vault_tags.py`, прогнати на двох відомих деградованих
файлах + кількох звичайних нотатках, лише потім `--apply`.
