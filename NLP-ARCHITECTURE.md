# WSM NLP Architecture (Vault Semantic MCP)

**Status:** ACTIVE (Оновлено 2026-08-27)
**Модель:** `BAAI/bge-m3` (XLM-R, 567M parameters)
**Апаратне забезпечення:** NVIDIA GeForce GTX 1050 Ti (4GB VRAM), CUDA 13.0 (через драйвер хоста), PyTorch 2.13.0+cu126.

## 1. Фундаментальні архітектурні принципи

Ця папка містить локальний ML-пайплайн для семантичної роботи з корпусом текстів (Sanskrit, Ukrainian, IAST).
Головний принцип системи: **Гібридна оркестрація (Lisp + Python / CUDA)**.
- **Python / PyTorch (`*.py`)**: Виконує роль виключно "математичного рушія" (tensor crunching). Завантажує ваги моделі в VRAM, перемножує матриці косинусної відстані і повертає сирі результати.
- **WSM / My-Lisp (`orchestrator.wsm`)**: Виступає мозком системи. Читає файли Онтології, керує розбиттям на партії (щоб не перевантажувати пам'ять) та ухвалює логічні рішення на основі векторної відстані через Lisp-правила.

## 2. Ключові компоненти та скрипти

1. **`embeddings.py`**
   - Обгортка навколо `BGEM3FlagModel` (бібліотека `FlagEmbedding`). 
   - Налаштування лежать у `config.json` (`"device": "cuda"`, `"use_fp16": true`). FP16 критично важливий для роботи на 4GB VRAM.

2. **`embed_corpus.py`**
   - Генерує базові вектори для всього `sanskritworld_texts`. 
   - Результат зберігається у `data/sanskrit_embeddings.jsonl`. Цей процес важкий і робиться одноразово або при додаванні нових текстів.

3. **`classify_corpus_semantic.py`** (Оновлений алгоритм 2026-08-27)
   - Динамічно зчитує всі нотатки з `🕉️ Онтологія`.
   - Рахує косинусну відстань між кожним текстом корпусу та кожним концептом Онтології.
   - **Правило порогу:** Ми відмовились від жорсткого ліміту `TOP_K=3`, щоб уникнути "сміттєвого" тегування (keyword matching). Натомість використовується суворий поріг **`THRESHOLD = 0.65`**. 
   - *Ефект:* Текст може отримати 10 тегів, якщо він дійсно охоплює 10 концептів, або 0 тегів, якщо він не відповідає жодному (що є сигналом для створення нового концепту).

4. **`orchestrator.wsm`**
   - Скрипт керування пайплайном, написаний на Lisp. Звертається до скриптів Python через системний примітив `(process-run)`.

5. **`embed_vault_live.py`**
   - Індексує весь живий Obsidian Vault для локального семантичного пошуку, ігноруючи системні папки (`.git`, `.obsidian`, `Corpus_IAST`).

## 3. Епістеміка та оточення

- **Ізоляція середовища:** Для запуску Python-скриптів використовується виключно спеціалізований venv: `/home/agents/GitHub/FlagEmbedding/.venv/bin/python`. Системний python3 не має доступу до CUDA.
- **Запобігання перевантаженню WSL:** При запуску ML-скриптів рекомендується обмежувати кількість CPU-потоків (наприклад, `export OMP_NUM_THREADS=2`), щоб парсинг JSON і підготовка даних не заморожували оболонку WSL, поки GPU вільний.
- **Епістемічний статус міток:** Усі згенеровані через косинусну відстань мітки зберігаються в `corpus_semantic_tags.suggestions.jsonl` зі статусом `semantic-suggest`. Векторна подібність — це лише **гіпотеза**, а не доведений факт. Фінальна інтеграція потребує доменного рев'ю агентів Shiva або Panini.

## 4. Процес розширення Онтології (Збагачення)
Оскільки BGE-M3 є векторною, а не генеративною моделлю, вона не здатна самостійно "вигадувати" нові концептуальні теги (Sparse Weights дають лише уривки слів, "subwords"). 
*Правильний пайплайн розширення:*
1. Знаходимо тексти, які не пройшли поріг 0.65.
2. Пропускаємо їх через LLM (або агента) для генерації абстрактної назви.
3. Створюємо `.md` файл у `🕉️ Онтологія`.
4. Наступний прогін `classify_corpus_semantic.py` автоматично підхопить новий файл і поширить його на всі семантично близькі тексти корпусу.
